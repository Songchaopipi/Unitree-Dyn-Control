# SRBD-MPC vs Full Single-Rigid-Body Analysis

This directory contains a Python-only research sandbox for testing whether the
`g1_srbd_ik_walk.cpp` SRBD-MPC formulation can stabilize a more complete
single-rigid-body (SRB) plant under the same controller parameters.

It intentionally ignores MuJoCo, leg IK, joint limits, and swing-foot
trajectories. The loop is:

```text
HLIP/LQR foot placement
  -> contact schedule and foot preview
  -> OSQP SRBD-MPC
  -> apply first foot wrench and ALIP contact locations to full SRB plant
  -> explicit Euler / SO(3) integration
```

The full SRB plant is a hybrid system here. The continuous control input is
the foot wrench, while the discrete/contact-geometry input is the touchdown
location generated by the ALIP foot placement planner. At touchdown, the
planner updates the corresponding foot position; the full SRB then uses that
position as the contact point for both the plant dynamics and the MPC preview.

## Files

- `math_utils.py`: rotation, quaternion, skew, foot wrench helpers.
- `models.py`: dataclasses for robot, gait, MPC, and simulation config.
- `alip_footstep.py`: C++ `FootPlacement::PlanHlipFootstep()` style HLIP/LQR foot placement planner.
- `osqp_srbd_mpc.py`: condensed standard SRBD-MPC QP.
- `full_srb_sim.py`: full single-rigid-body Euler integrator.
- `run_g1_srbd_full_srb_analysis.py`: runnable experiment script.
- `requirements.txt`: optional Python dependencies.

## Dependencies

The preferred QP backend is OSQP:

```bash
python3 -m pip install -r theory_anylisis/requirements.txt
```

If `osqp` is not installed, the script falls back to `scipy.optimize.minimize`
so that the structure can still be run and inspected.

## Run

From the repository root:

```bash
python3 theory_anylisis/run_g1_srbd_full_srb_analysis.py
```

Edit the `CONFIG = RunConfig(...)` block near the top of
`run_g1_srbd_full_srb_analysis.py` to change duration, gait, MPC, CSV, plot,
and animation settings. For example, set these fields for a headless CSV run:

```python
csv=Path("theory_anylisis/out.csv")
animate=False
print_wrench_summary=True
```

The default now solves MPC every simulation step for the cleanest research
baseline. To test the C++ demo solve cadence while still forcing a resolve at
contact switches, set:

```python
mpc_solve_every=5
```

More aggressive test:

```python
vx=0.18
vy=0.03
yaw_rate=0.15
duration=10.0
plot=True
```

Lightweight 3D rigid-body replay is enabled with:

```python
animate=True
vis_stride=10
```

In the animation, orange squares are active feet, gray squares are inactive
feet, red arrows are applied GRFs, and the green cross is the ALIP next
touchdown target.

Try real-time playback:

```python
animate=True
realtime=True
vis_stride=5
```

## What This Tests

The MPC model uses the simplified SRBD dynamics:

```text
rpy_dot   = Rz(yaw) omega
p_dot     = v
omega_dot = I_W^-1 sum_i ((p_foot_i - p_com) x f_i + tau_i)
v_dot     = (1 / m) sum_i f_i - g e_z
```

The simulated plant uses the fuller SRB rotational equation:

```text
I_W omega_dot + omega x (I_W omega) = sum_i ((p_foot_i - p_com) x f_i + tau_i)
```

and integrates attitude on SO(3). If the same SRBD-MPC parameters remain stable
on this plant, the simplified controller has a useful robustness margin for
the missing gyroscopic and nonlinear attitude terms.

## Stabilization Notes

Earlier debugging found two implementation issues that are independent of the
standard SRBD-MPC objective:

- Reusing an old single-support wrench across a contact switch could leave the
  new support foot with a zero wrench for a few milliseconds.
- The footstep preview needs the same target-yaw/current-yaw split used by the
  C++ foot-placement code.

The current controller therefore keeps the standard SRBD-MPC cost, forces an
MPC resolve when contacts change, and keeps the C++ HLIP/LQR step limits of
`0.10 m <= |step_y| <= 0.60 m`.
